## Шаг 1. Каркас пакета и установка

**Делаем:** `package.json` (SPEC §8), `cordis.patch.yml` с одной `insert`-строкой `prompt-profiles`,
пустые `lib/index.js`, `lib/section.js`, `lib/profile.js`, `lib/client.js`; `yaml` в зависимостях,
`pnpm install` в каталоге бандла.

**Готово когда:** пакет ставится и включается; строка `prompt-profiles` видна в композиции.

**Проверка:** `plugin_manager { action: 'install_bundle', target: '/home/knopki/.dsh/bundles/dsh-prompt-profiles' }`,
затем строки `prompt-profiles` в `~/.dsh/profiles/web/package.json → dsh.profile.bundles` и в логе лоадера.
Помнить: замена уже установленного пакета требует рестарта, первая установка может подняться через HMR.

## Шаг 2. Mirror, реестр, subpath-плагины

**Делаем:**
1. `lib/builtin-orders.js` — копия `SECTION_ORDERS` из `dsh-system-prompt` (на 0.1.7-rc.1: от `-1000` до `10200`).
2. Парсер mirror: чтение `lib/index.js` установленного `@deepseek-ai/dsh-system-prompt` (резолв от
   каталога профиля из `profileContext.dir`), регулярное извлечение таблицы; фолбэк на копию + варнинг.
3. Сервис `ctx.promptProfiles` с `registerSection/registerProfile/sections/profiles/builtinOrders`.
4. `lib/section.js` и `lib/profile.js`: `static inject = ['promptProfiles']`, регистрация своего config
   через `ctx.effect`, снятие при dispose; `configure({auto:false})` для settings.

**Готово когда:** вставленная руками строка-секция и строка-профиль появляются в `sections()`/`profiles()`;
`disabled: true` убирает их; дубликат `config.id` даёт варнинг и детерминированного победителя.

**Проверка:** временный отладочный роут `GET /__dsh-prompt-profiles/state` (он же пригодится в шаге 4).

## Шаг 3. Ядро: разрешение, снапшот, инъекция

**Делаем:**
1. Домен `prompt_profiles` (SPEC §5.4) через `ctx.storageDomain`.
2. Слушатель waterfall `system-prompt/assemble` (SPEC §5.3): строит `workspaceKeys` без дублей
   (членство сессии → `resolveByPath(cwd)` → сырой cwd → workspaceId); выбирает по первому
   присутствующему ключу `lastByWorkspace` (включая `''` = none; stale id сразу fallback на default),
   default использует, только если ни одного кандидата нет. `/last` пишет под первым кандидатом,
   а чтение сохраняет доступ к историческим UUID/path-ключам; path-ключи не удаляются только из-за отсутствия в реестре, поэтому работают и на поверхностях без workspace. Затем `buildSnapshot`, durable-first
   запись снапшота при первом шаге сессии,
   вставка секций в `assembly.sections` с `prompt-profile:<id>` и порядком из профиля без смещения;
   одинаковые order допустимы, сортировка детерминирована по `(order, позиция в профиле)`, при
   равенстве с присутствующей built-in наша секция вставляется перед ней; фильтрация по `scope` (с учётом результата R5).
3. Пустой профиль/отсутствие профиля → слушатель не делает ничего вообще.

**Готово когда:** на новой сессии маркерные секции видны в промпте в правильном порядке; повторный
шаг сессии не перечитывает конфиг; правка секции во время сессии на неё не влияет; resume даёт тот же промпт.

**Проверка:** сценарии — (а) профиль выбран, (б) профиль не выбран, (в) профиль с пустым списком,
(г) ссылка на удалённую секцию, (д) два профиля подряд в одной сессии (смена «на лету» не действует),
(е) resume после правки тела секции.

## Шаг 4. Writer и API

**Делаем:**
1. `lib/writer.js`: чтение/запись профильного патча через eemeli `yaml` с customTags `!!js`,
   создание `insert`-строк, удаление своих строк, `disabled: true` для чужих, бэкап и откат на время
   батч-операций, внутрипроцессный мьютекс.
2. Роуты `webServer` (SPEC §5.5) + валидация входа по схемам из §4.
3. Обновление существующих section/profile rows — через `ctx.settings.replace(rowId, volatileFields, expectedRevision)`; `/default` — точечный `settings.mutate`, `/last` и чистка ссылок — per-key mutate ops.
4. `section/rename` — один writer-коммит меняет только `config.id` и id строки секции (новая строка → снятие старой); профили не меняются. Ответ включает `affectedProfiles: [{profileId, title}]` для оставшихся старых ссылок; повторный rename в тот же id — 400; при ошибке — восстановление файла.

**Готово когда:** CRUD по API не ломает комментарии и `!!js` в патче, HMR пересобирает композицию,
rename не меняет профили и сообщает в `affectedProfiles` о оставшихся старых ссылках, удаление чужой строки даёт `disabled: true` в профильном слое.

**Проверка:** прогон каждого роута curl'ом с последующим `git diff`-подобным сравнением файла;
попытка испортить входные данные (пустой title, order не число, чужой id) — отказ без записи.

## Шаг 5. Клиент: чип

**Делаем:** `lib/client.js` — обёртка `__ModuleLoader__.load`, регистрация в `conversation.input.left`
(id `prompt-profile`, order 10): меню `none` + профили по алфавиту + `Manage profiles…`, запись `last`
при явном выборе, `null` для непустой сессии и при отсутствии профилей, `Toast` на ошибку.

**Готово когда:** чип виден на пустой сессии рядом с `permission` и `plan`, выбор профиля применяется
к новой сессии и запоминается для воркспейса, после первого хода чип исчезает.

**Проверка:** два воркспейса — у каждого свой последний профиль; удаление профиля, на который ссылается
`last`, даёт тихий сброс на `default`.

## Шаг 6. Клиент: страница редактора

**Делаем:** `settings.section` (id `prompt-profiles`, order 25) — SPEC §6.2: три таба
Profiles / Sections / Preview с drill-down внутри таба (`← back`, Esc, повторный клик по табу),
автосейв с дебаунсом. Таб Profiles: список + «Default for new sessions» + состав профиля как outline
с built-ins из mirror, кнопка `+ Add section` (пикер с поиском и мультивыбором); порядок задаётся
числовым полем и перетаскиванием только внутри состава, клавиатурный путь — числовое поле. Таб Sections: поиск, `used in`,
`source`, форма секции (title + body, «используется в» read-only, без scope). Таб Preview: наши
секции в порядке, built-ins плейсхолдерами, пропущенные — с причиной. Доступные примитивы:
`Menu`, `Tag`, `Switch`, `Toast`, `Tooltip`, `SegmentedTabs`, `DisclosureRow`,
`SettingsForm`/`SettingsValueField` и иконки `Icon*Medium/Regular`.

**Готово когда:** все операции выполняются из UI, а результат совпадает с тем, что даёт ручная правка
профильного патча; пустое тело и битые ссылки деградируют с предупреждением, а не с падением.

**Проверка:** сценарий «создать секцию → добавить в профиль → выбрать профиль → начать сессию →
увидеть текст в промпте»; сценарий «переименовать секцию, используемую в двух профилях» — проверить `affectedProfiles` с обоими профилями и отсутствие изменений их ссылок; сценарий
«удалить секцию из бандла» (получаем `disabled: true`); навигация — drill-down и возврат работают
из всех трёх табов, автосейв не дублирует записи при быстром наборе.

## Шаг 7. Полировка и e2e

**Делаем:** предупреждения (missing section, disabled section, битый mirror, complete-mode),
сообщения в лог, аккуратные пустые состояния, en-локаль через `dsh-client-locale`.

**E2E-чеклист:**
1. профиль не выбран нигде → промпт не изменён (побайтово сравнить с сессией без бандла);
2. `default` задан, `last` пуст → применяется `default`;
3. явный выбор → применяется он и запоминается; новая сессия в том же воркспейсе — он же;
4. другая поверхность (не web) в том же воркспейсе → применяется `last`;
5. `scope: main-only` не протекает в субагента; `inherit` протекает; fork наследует всё;
6. порядок секций соответствует outline; одинаковые order допустимы, ничего не смещается; при равенстве с присутствующей built-in своя секция вставляется перед ней;
7. правки конфига и удаление профиля не влияют на идущую сессию; resume воспроизводит промпт;
8. сессия в mode `minimal` → предупреждение видно в UI.
